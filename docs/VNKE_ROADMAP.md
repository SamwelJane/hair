# Vietnam → Kenya Managed Commerce & Fulfilment Platform — Roadmap

This document tracks the evolution of this codebase from a single-shipment
hair/wig e-commerce platform into a **Vietnam → Kenya Managed Commerce &
Fulfilment Platform**: Supplier → Cherubim Vietnam Warehouse → International
Freight → Kenya → Customs → Customer, under the promise "Buy from Vietnam.
We handle the rest." It is an *evolution* of the existing system, not a
rebuild — every phase below extends existing modules (pricing, auth,
payments, orders, tracking, admin) rather than duplicating them, and no
phase is done until DB + API + business logic + authorization + UI +
validation + notifications + audit + tests all exist for it (see
"Definition of Done" at the end).

Status: **All in-scope phases (0-12) complete.** Phase 8 (Kenya Fulfilment) is dropped from scope (see that section) - it is the only phase from the original 12-phase plan not implemented.

**Scope note (added after Phase 2/3 execution):** the original Phase 2 plan below described renaming `Shipment` → `InternationalShipment` and `ShipmentMilestone` → `TrackingEvent` as part of Phase 2's migrations. In practice that rename was deferred — it would have broken every existing call site (`routers/admin/orders.py`, `routers/tracking.py`, `services/order_state_machine.py`, `tests/integration/test_tracking.py`) before Phase 3's replacement logic existed to take over. Phases 2 and 3 as actually implemented are purely additive: the new `Package`/`Consolidation`/`Customs`/`Exception`/`Warehouse`/`ExternalShipment` tables and the new `Order.tracking_number` column were added without touching the legacy `Shipment`/`ShipmentMilestone` model or the admin-driven shipment-creation flow at all. That legacy flow (its own `HB-` prefixed tracking numbers, entirely separate from the new `VNKE-`/`VNKE-EXT-` ones) still works exactly as before and all of its tests are untouched. The `Shipment` → `InternationalShipment` rename now belongs to Phase 6 (International Logistics), when `Consolidation`-linked shipments actually need to replace the old one-shipment-per-order model.

## Phase 3 — Tracking Foundation ✅ done

Implemented with a **much lower-risk scope than originally planned above**: instead of generalizing the legacy `generate_tracking_number()` and touching `routers/admin/orders.py`/`routers/tracking.py`/`test_tracking.py` (a genuine breaking change to working, tested behavior), Phase 3 added two brand-new generator functions — `generate_order_tracking_number()` (`VNKE-YYYYMMDD-XXXXXX`) and `generate_external_shipment_tracking_number()` (`VNKE-EXT-YYYYMMDD-XXXXXX`) — in `services/tracking_numbering.py`, both checking uniqueness across **both** `Order.tracking_number` and `ExternalShipment.tracking_number` via a shared `_is_taken()` helper. The legacy `generate_tracking_number()` (`HB-` prefix, checks only `Shipment.tracking_number`) and everything that calls it (`routers/admin/orders.py::create_shipment`, `routers/tracking.py`, `test_tracking.py`) were **not touched at all** and remain fully functional, untested-change-free.

- `routers/orders.py::checkout` now generates the order's tracking number in the same transaction as `order_number`, before insert — atomic, immutable from that point on.
- `Order.tracking_number` is `NOT NULL` (migration `797d302acfa3`, with a backfill step for any pre-existing NULL rows before adding the constraint — none existed in practice, this is a young schema).
- `CheckoutResponse`, `OrderOut`, `OrderListItemOut`, `AdminOrderListItemOut`, `AdminOrderDetailOut` all now expose `tracking_number`.
- `services/external_shipments.py` was deliberately **not** created yet — `generate_external_shipment_tracking_number()` exists and is unit-tested, but the service/router/schema that would actually call it lands in Phase 4 together with the rest of the warehouse external-shipment-intake flow, so nothing sits unexercised by any endpoint.
- Public tracking (`/track/{tracking_number}`) was **not** extended to resolve the new `VNKE-`/`VNKE-EXT-` numbers yet — there's nothing meaningful to show for one until Phase 4+ gives it packages/events. Extending it is now explicitly Phase 4/9's job, not Phase 3's.

New tests: `tests/unit/test_tracking_numbering.py` (format, collision-retry-then-succeed, gives-up-after-5-attempts, cross-table namespace sharing), plus assertions added to `test_checkout.py` (`tracking_number` present in the checkout response and matches the persisted `Order` row) and `test_orders.py` (`test_tracking_number_is_immutable_across_status_transitions`, walking PAID→RECEIVED_AT_OFFICE via the admin status endpoint and asserting the tracking number never changes).

**Regression caught and fixed during Phase 3 verification**: `tests/integration/test_products_public.py` constructed an `Order` row directly via the ORM (bypassing checkout) without a `tracking_number`, which started failing once the column went `NOT NULL`. Fixed by adding a `tracking_number="VNKE-TEST-0001"` value there; a repo-wide grep confirmed no other direct `Order(...)` construction site was missing one.

`packages/api-client/src/schema.ts` was regenerated against a locally-run instance after these changes; `frontend`/`mobile` both still build/typecheck clean against it (neither has UI that reads `tracking_number` yet - that's Phase 9).

## Phase 6 — International Logistics ✅ done

Delivered the deferred `Shipment`→`InternationalShipment`/`ShipmentMilestone`→`TrackingEvent` rename, with one architectural change from the original plan:

**`InternationalShipment` was not built as a separate table.** Once actually designing it, `Consolidation` already carried everything a shipment needs (freight fields, a full `OPEN→...→ARRIVED→CLOSED` lifecycle) — a second table would only have normalized the same 1:1 row across two tables with no behavioral benefit, and the spec itself warns against parallel implementations. Instead, `Consolidation` gained `shipment_code` (`SHP-VNKE-######`, generated the moment it goes `IN_TRANSIT`), `carrier`, `carrier_tracking_reference`, `current_location`, and `estimated_arrival` — so the same row carries both its internal `CON-VN-######` warehouse-batch identity and its external, carrier/customer-facing `SHP-VNKE-######` shipment identity, matching spec section 6's separate-identifier requirement without a redundant model. This is documented directly in the `Consolidation` model's docstring for anyone who goes looking for `InternationalShipment` later.

**The legacy flow was fully retired, not left running in parallel**: `models/shipping.py` (`Shipment`/`ShipmentMilestone`) deleted; `routers/admin/orders.py::create_shipment`/`add_milestone` removed (replaced by a `packages` list on `AdminOrderDetailOut` showing each package's code/status/consolidation/shipment code); `services/order_state_machine.py`'s shipment-status-sync block removed (order status and package/shipment status are now properly independent state machines, as the spec always wanted); `services/tracking_numbering.py::generate_tracking_number` (the `HB-` generator) deleted as dead code; `services/analytics.py`'s two `Shipment`-based queries reimplemented against `Consolidation` (`shipments_in_transit`) and `Order`+`Package` (`total_shipments`/`avg_profit_per_shipment_usd` — now "orders with a received package" rather than "orders with an admin-created Shipment record").

**Public tracking (`/track/{tracking_number}`) was rewritten**, closing the gap flagged back in Phase 3: it now resolves `Order.tracking_number` or `ExternalShipment.tracking_number`, finds the owning Package(s), and returns a combined status (least-advanced package wins, except `EXCEPTION` always bubbles up regardless of other packages' progress; falls back to `Order.status` if no package has been received yet), a per-package breakdown, and the merged `TrackingEvent` timeline. `frontend/src/features/tracking/TrackingPage.tsx`, `mobile/src/app/track/[trackingNumber].tsx`, and `frontend/src/features/admin/OrderDetailPage.tsx` were all updated for the new response shape.

**New `TrackingEvent` model** (append-only customer-facing timeline, spec section 25/57) with a `services/tracking_events.py::add_event()` helper, wired into the warehouse pipeline built in Phases 4-5: package receive → "Received at Cherubim Warehouse", QC pass → "Package Verified", added to consolidation → "Consolidated", consolidation departs → "Departed Vietnam", marked in transit → "In Transit to Kenya", arrives in Kenya → "Customs in Kenya". The first four timeline steps (Order Placed, Payment Confirmed, Supplier Confirmed, Processing) are commercial-order events, not logistics ones — deliberately left to Phase 9, which can synthesize them from the existing `OrderStatusHistory` table rather than needing new `TrackingEvent` rows.

## Phase 11 — Security & QA (complete)

**RBAC audit.** Every one of the 28 `/warehouse/*` endpoints across `consolidations.py`/`customs.py`/`dashboard.py`/`external_shipments.py`/`packages.py` was checked against `core/permissions.py::ROLE_PERMISSIONS` - all 28 carry a `require_permission(...)` gate (confirmed by counting `@router.` decorators against `require_permission` call sites; none accidentally public). One real gap was found and fixed: `arrive-kenya` and `POST /{id}/exceptions` were gated behind `consolidation.close`, which only ADMIN/STAFF/WAREHOUSE hold - meaning `KENYA_OPS`, whose entire job is the Kenya-side of this pipeline, could not confirm their own shipment had arrived or flag a problem with it once it had. Covered by a new test, `test_kenya_ops_can_confirm_arrival_and_report_exceptions`, in `test_warehouse_consolidations.py`.

These were defined during Phase 4 planning but never wired to any endpoint once the design settled on `require_permission(...)` exclusively - left in place they read as the active gating mechanism to a future reader, when they were actually inert.

**`docs/DATA_PRIVACY.md`** rewritten in full: legacy `src/lib/...` paths replaced with the current `backend/app/...` ones, and three new sections added covering data this roadmap introduced - external-shipment guest-customer contact details (no `users` row exists for that person at all), package photos/QC/customs declaration data, and the deliberate label-masking (`mask_customer_name`) and PII-free public tracking page that were already implemented in earlier phases but never documented here.

**Idempotency review** (no code changes - a review of what already exists): tracking-number generation (`tracking_numbering.py`) retries on collision up to 5 times against a shared namespace check across `Order` and `ExternalShipment`, the same check-then-generate pattern already used pre-roadmap for `order_number`/`package_code`; a true concurrent-request race is theoretically possible but astronomically unlikely (36^6 combinations) and consistent with existing codebase convention, not a regression introduced by this work. Duplicate warehouse scans are rejected per (order, supplier_order) pair (`DuplicateReceiptError`, tested). Label print vs. reprint are distinct operations/audit actions that never mutate the tracking number (tested). `mark_in_transit`'s one-time `shipment_code` generation is protected by its own state-machine precondition (`DEPARTED` only) rather than needing separate idempotency logic. Duplicate M-Pesa callbacks are already a no-op past the first resolution (`apply_mpesa_callback`, pre-existing, tested).

**State-machine review**: confirmed no service module writes another entity's status field except as part of one documented, causally-connected business event - e.g. `services/consolidation.py` advancing member `Package.status` when the parent `Consolidation` transitions (add/depart/arrive), and `services/customs.py::clear` advancing both `Consolidation` and `Package` status when a declaration clears. This mirrors the pre-existing precedent in `services/payments.py`, where a successful payment callback advances `Order.status` alongside `Payment.status` - it is not a violation of the "separate state machines" rule (which is about not merging distinct concerns into one giant enum, and was achieved: `OrderStatus`/`PackageStatus`/`ConsolidationStatus`/`CustomsStatus`/`PackageQCStatus`/`PackageCondition`/`ExternalShipmentStatus`/`OpsExceptionType`/`Severity`/`Status` remain ten separate enums), just an aggregate root's service correctly cascading one real-world event across its owned children.

**E2E suite** (`tests/integration/test_e2e_fulfilment.py`, new file): most of spec §59's scenario list already had focused coverage elsewhere (duplicate payment callback: `test_payments.py`; duplicate warehouse scan and reprint label: `test_warehouse_packages.py`; customs query: `test_warehouse_customs.py`) - rather than duplicate those, this file adds the scenarios that specifically require one continuous walk across multiple services to prove they compose correctly: `test_platform_order_full_lifecycle_from_placement_to_customs_cleared` (order → payment → full warehouse/customs pipeline → `READY_FOR_DELIVERY`, asserting tracking-number immutability, the customer order-detail packages view, and both Phase 9 notifications firing in order), `test_external_shipment_full_lifecycle_reaches_customs_cleared` (same pipeline for a non-platform customer with no `User` row at all), `test_multi_package_order_customer_view_reflects_every_package` (extends `test_tracking.py`'s existing combined-status coverage to also check the Phase 9 customer-facing packages list), and `test_failed_mpesa_payment_leaves_order_unpaid_with_no_fulfilment_side_effects` (a genuinely missing case - no existing test exercised the M-Pesa failure callback path at all).

**Infrastructure incident, worth recording**: mid-phase, two `pytest` runs were started concurrently against the same shared Postgres test database (each test's `_clean_database` autouse fixture does a full `drop_all`/`create_all`). This produced a real deadlock between the two sessions' DDL statements, both stalling with no progress. Stopping both processes did not fully resolve it - one backend was left `idle in transaction` mid a `CREATE TYPE ...` statement (a connection whose client process had already been killed, but Postgres hadn't yet noticed), which continued blocking every subsequent test run's `DROP TYPE`/`CREATE TYPE` calls until it was found via `SELECT pid, state, query FROM pg_stat_activity` and force-closed with `pg_terminate_backend(pid)`. Lesson for future sessions: never run two `pytest` invocations against this backend concurrently, and if a test run is ever killed mid-flight, check `pg_stat_activity` for an orphaned `idle in transaction` session before assuming a subsequent hang is a code problem.

All pass; full regression suite (run once, cleanly, after resolving the above): 235 passed, the same 1 pre-existing unrelated failure (`test_update_pricing_settings`) carried since Phase 0.

## Sequencing & risk
Phase 0 lands alone, first (blocks CI) — **done**. Phases 1-3 are strictly sequential (each depends on the prior's schema/service). Phase 4 depends on Phase 3's tracking relocation being complete and tested. From Phase 5 onward, work can parallelize: one track on Consolidation → Logistics → Customs (5-7), another on Reporting (10) once enough data exists to query. Phase 8 (Kenya Fulfilment) is dropped from scope. Customer Experience (9) should trail whichever of 5-7 lands first. Security & QA (11) and Production Readiness (12) are final gates, not parallelizable with the rest.

The highest-risk single change in the whole roadmap is the Phase 2/3 `Shipment` → `InternationalShipment` refactor plus tracking-number relocation, since it's a genuine breaking change to already-tested, working behavior (`test_tracking.py`) — treat Phase 3 as a hard checkpoint: verify both the platform-order and external-shipment tracking paths, and reprint-idempotency, before starting any Phase 4 warehouse work on top of it.
